父方递进来一件任务，核心按什么顺序做什么事，每一步为什么。

1名词（全文只用这些词）

词 指什么
父方 把任务交给核心的一方。模型、别的代码，都算。
子代理 核心起的一个独立进程。它接了任务就去做，做完交回结果。
任务 父方给的一段文字。子代理照这段文字去做。
理由 父方额外给的一段文字，告诉子代理为什么派它。可以被主方关掉——关掉时内容丢掉，但记录里会留一笔「理由被丢了」。
记录 一次派发留下的一行数据。核心只有记录，没有别的状态。
收据 子代理实际做过的事。从子代理的输出里读出来的，不听子代理自述。
报告 子代理交回的一段结构化摘要。子代理可以不给。
正文 子代理的最后一段话。这才是交付物。
座位 核心门口的一个工位。一个座位同时只站一个子代理。座位有限，站满了就在旁边排队等。
安检 接任务之前要过的检查。不过就退回。
写程序 子代理自己写一段脚本，脚本里批量调工具。只有开了这个的子代理能做。
池子 核心能从这台机器上分到的一块资源。座位是从池子里切出来的份额。
通知 跑完了的消息，按批发给父方。
转向 子代理还在跑的时候，父方插进去的一句话。孩子在下一个回合边界看到它，调整方向继续干；不打断正在跑的工具。
信箱 转向落盘的那个 JSONL 文件。父方往里追加，子代理在每个回合边界读新增的行。
送达证据 从子代理的事件流里认出来的投递痕迹（进队列 / 进 transcript / 下一轮真的带着它跑了）。不听子代理自述。
未送达 退出时只有一个证据都没有的 sent。明说没送到，不装成功。

2核心做什么、不做什么

做

  • 拦——不该接的任务，当场退回并说清为什么
  • 排——手上的任务多了就排队等。等，不拒
  • 看——子代理卡住不动了，把它收掉
  • 记——每次派发都写一条记录
  • 分池——按机器实际情况决定能开几个座位

不做

  • 不决定该派几个
  • 不决定该派什么
  • 不干活——活是子代理干的
  • 不碰 GPU——那是子代理内部的事
  • 不跑程序——写程序是子代理的能力

一句话的设计立场

子代理的话不可信——报告、黑板留言、自述的自检都只是线索。但父方看到的「动作」也只是字节： 闸能保证的只有 spawn 之前的输入形状；spawn 之后，同 UID 的孩子能写记录、信箱、产出与黑板。 所以判据是「有没有实测证据」，不是「是谁说的」。

3池子：座位从哪来 这次新写

座位不是拍脑袋定的数。它是池子切出来的份额。

读机器情况，要分「恒定的」和「波动的」

读什么 会不会变 什么时候读
总内存 不会变——机器的规格是固定的（内存条插拔不是日常操作） 启动时读一次，存起来
核数 不会变 启动时读一次，存起来
此刻已用多少 一直在变——别的进程进进出出 每次派发前重读

⇒ 启动时读一次的是「机器多大」，每次重读的是「机器现在挤不挤」。

启动时：算出座位上限（之后不变）

读一次机器规格 总内存多少、几个核。存起来，之后不再读。
算出座位上限 总内存的 10% 是预留；每座份额 = max(512 MiB, 总内存的 2%)（已实测校准）。
预留怎么算 总内存的 10%。跟「还剩多少」无关，是按总量算的。
每座份额 max(512 MiB, 总内存的 2%)——512 MiB 是实测校准的下限。座位上限 =（启动时的可用 − 预留）÷ 每座份额——用启动时的可用，不是总内存。

每次派发前：重算此刻的池子

读一次此刻已用多少 就读这一样。总内存和核数不用再读（启动时存着呢）。
算出此刻的池子 还能马上用多少 − 预留
此刻还能再开一个吗 此刻的池子 ÷ 每座份额 ≥ 已经在跑的 + 1 ？
够 → 开 正常起。
不够 → 排队等 等。不拒绝——等下次重算时池子松了就能开。

为什么要每次重算

内存是波动的。启动时算的池子只反映那一刻：

  • 用户在这期间开了个吃内存的东西 → 池子变小，不该再开新的
  • 用户关掉了它 → 池子变大，可以多开几个

⇒ 重算的成本很小（实测读一次机器内存约 3 毫秒），每个派发前读一次完全可以。

用演算说明：机器挤不挤，池子会自己变

总内存 别的进程吃掉 还能用 扣掉预留 池子 此刻能开几个
8192 MiB 60%（4915.2） 3276.8 −819.2 2457.6 4 个
8192 MiB 90%（7372.8） 819.2 −819.2 0 0 个

这台机器的每座份额：8192 × 2% = 163.8 MiB，低于 512 MiB 的下限 ⇒ 取 512 MiB。总内存超过 25600 MiB 时，2% 才超过下限（25600 × 2% = 512）。

机器太挤 ⇒ 一个都不开，这是正确答案

占用到 90% 时池子是 0 ⇒ 不派任何子代理。不是 bug，是「机器已经很挤了，别再开新的」。
而且这是此刻的判断——过一会儿内存松了，排队等着的那个就能开了。

三个数要定死

  • 预留比例：总内存的 10%（已定）
  • 每个座位的份额：max(512 MiB, 总内存的 2%)（已实测校准——一个子代理的峰值 RSS 约 148 MiB，512 MiB 是它的 3.5 倍；同一台 24 GiB、可用 5.2 GiB 的机器上，按 10% 只够开 1 座，按 512 MiB 是 5 座）
  • 座位数可能是 0：机器启动时就很挤就该是 0。不要加「最少开 1 个」的下限——那会跟上面的演算打架

失败方向是不对称的，所以宁可保守

池子给大了 内存不够 → 机器开始换页 → 所有子代理一起变慢，甚至被系统杀掉
池子给小了 只是少开几个座位。没有任何坏处

⇒ 默认值往保守那一侧偏。

「已用」怎么算（两个系统不一样）

怎么读 「还能用」是什么
Linux free 命令 空闲 + 缓冲 + 缓存
macOS 没有 free，要读 vm_stat 自己算 空闲 + 不活跃（文件缓存，可回收）+ 预读 + 可清除

总内存和核数在两个系统上都是恒定的（macOS 用 sysctl，Linux 用 /proc）——启动时读一次就够，别放进每次重算里。

三个坑

  • macOS 的「不活跃」是文件缓存——可回收，但回收有延迟。算进「还能用」是乐观的。
  • 每次派发前重算（实测读一次约 3 毫秒，不心疼）。但重算只用来「决定还能不能开新的」，绝不用来「把已经在跑的收掉」。收缩等于中途杀子代理，与「派出去的活不该被随便弄死」冲突。
  • 只重读「已用」，不重读「总内存」和「核数」。那两个是恒定的，启动时读一次存起来就行——每次重读是白花时间。
  • 排队等的任务不会自动开起来。它要等下一次有人来派发、触发一次重算，才知道自己能不能开。要它自己醒，得有人定时叫醒它（这条要定，见下）。

「重算」带来的一个新问题：排队的任务谁来叫醒

池子紧了 ⇒ 任务排队等。但池子什么时候松，没人知道。

三种做法：

  • 谁来派发就重算一次——最省事，但「没人派发时池子松了」就浪费了（队列一直卡着）
  • 定时重算（比如每秒一次）——队列能自己醒，但要一直跑一个定时器
  • 子代理跑完时重算——有子代理结束就顺便看一眼，队列能跟着动

⇒ 三条一起用最稳：每次派发前重算 + 子代理结束时重算 + 一个慢的定时器兜底。

4CPU：不是决定座位，是决定「别一起冲」 这次新写

子代理不是吃 CPU 的东西

子代理 99% 的时间在等模型响应，CPU 占用接近 0。所以核数不决定座位数。

但它启动那一下要吃 CPU：起一个 pi 进程约 0.2 秒 CPU 时间。同时起 8 个 = 8 个核各忙 0.2 秒（不是「全核 1.6 秒」）——这时候父方也会跟着变慢（它跟子代理在同一台机器上）。

现在有几个正在启动 同时启动数 ≤ 核数 ÷ 2，夹在 1 到 4 之间
没到上限 → 启动 正常起。
到了 → 稍等 等一会儿再起。不影响座位数——座位照占，只是起得慢一点。

为什么这么定

  • ÷ 2：留一半核给父方和系统。父方自己也在跑模型、也在解析工具结果。
  • 上限 4：启动再快也就 0.2 秒。节流到 4 个一批，8 个子代理分 2 批，多花 0.2 秒——这个代价可以忽略（子代理要跑几分钟）。
  • 下限 1：单核机器也要能一个一个起。
  • 不读实时 CPU 负载：读一次要起一个进程（几百毫秒），而且负载是波动的，读到的瞬间可能已经变了。用「核数」这个静态量算更稳。

子代理自己吃 CPU 的两种情况，不管

① 大目录查找（多线程的查找工具）② 上下文压缩（序列化 + 剥类型）。

要 8 个子代理同时撞上这两种才出事，概率极低。要管就得给每个子代理限核（操作系统层的事，跨平台麻烦）。接受这个风险。

5能不能写程序：一条路，一个参数 这次新写

先说清楚：不是两条路

子代理只有一条路。写不写程序，只是起它的时候多带一样东西。

普通 能写程序
记录结构 同一个
安检 同一套
座位池 同一个
卡住判定 同一套
收东西 同一套
起它的命令 基础命令 基础命令 + 两样

⇒ 别建两条代码路。就是一个开关，透传到拼命令那一步。

开关叫什么、谁来决定

参数名：allowScripts

这个开关是派发参数，父方每次派任务时决定。不叫 writePrograms（会跟兄弟仓的 writeProgram 撞脸，那是把程序源码写盘的方法，完全无关）。

父方这次派任务，开不开 allowScripts: true 或 false。不传 = 用会话的默认值。
开了 → 这个子代理能写脚本 同一形态调很多次时，它自己写一段脚本批量跑。
关了 → 一次调一个工具 照旧。
核心：收到一个布尔值，透传下去 核心不知道它意味着什么，只知道「拼命令的时候要带上它」。
拼命令那一步 开关开着 ⇒ 多带两样。这是唯一跟 pi 有关的地方。

「不传 = 用会话默认值」怎么实现

启动时外壳读用户设置（有没有 +codemode），把它作为默认值交给核心；每次派发父方可以覆盖它。

⇒ 核心只存一个默认值、收一个可选覆盖。它仍然不认识 pi——那个默认值是谁算的，核心不知道。

参数描述怎么说（模型看的，必须准确）

这段要一字不差地写进参数描述

allowScripts 的描述：

true = 这个子代理能写脚本批量调工具：脚本里可以循环、并行调工具，只有脚本的输出回到模型（中间结果不进上下文）。
适合「同形态调用很多次」的机械活——批量读文件、批量改、批量查。
代价两条：① 子代理的输入会多一份工具声明（吃 token）；② 它不保证子代理真的会写脚本——要它写，就在任务里明说「用写脚本的方式」。
不传 = 用会话的默认值。

⇒ 最后那句「不保证真的会写」必须留着。实测过：光靠提示词劝模型写脚本没用（10 次里 0 次）。不写这句，父方会以为开了就会用。

描述里三个不能省的

  1. 它省的是什么——中间结果不进上下文。不说清，模型不知道开了有什么好处。
  2. 它花的是什么——多一份工具声明。不说清，父方会到处乱开。
  3. 它不保证什么——不保证子代理真会写脚本。不说清，父方会等一个不会来的省 token。

多带哪两样（真机验过）

带什么 为什么 不带会怎样
-e 内建:codemode 把写程序的能力显式带进来（命令行给的扩展不受减量旗标影响） 减量旗标会把它砍掉 ⇒ 子代理看不见这个能力
--tools 名单里加上它 工具名单不含它 ⇒ 被名单砍掉 能力带进来了也调不到

要不要改名单，看有没有收窄

这次收窄工具了吗 带什么
没收窄（默认） 只带 -e 就够——所有工具都在，能力自然可用
收窄了（只读档位） -e ＋ 名单里加上它

⇒ 只带 -e、名单里却没有它 ⇒ 能力进来了但被名单砍掉，模型还是看不见。这是实测踩过的。

pi 1.5.2，每行都真的起了一个子代理。

为什么要这个开关：少派子代理

每多派一个子代理，就要多付一次固定开销（实测每个约 7.6k 输入 token）。

做法 固定开销 中间结果
派 8 个普通子代理 8 份 每个的中间结果各自进各自的上下文
派 1 个能写程序的子代理 1 份 脚本里的调用不进上下文

但它省的不是「服务端缓存」

实测过：每任务一个新进程的形态拿不到前端缓存的红利。省的是固定开销 + 中间结果不进上下文。

这是「能不能用」，不是「会不会用」

这一节只保证能力在子代理面前。至于模型愿不愿意写程序，实测过：在 pi 那边，光靠提示词劝模型写程序没用（10 次里 0 次）。要它写，得直接要求「用写程序的方式」。

两个参数这次不做：标签、预设

标签——本来打算加一个「给人看的一句话名字」，因为编号是 UUID，人认不出来。

⇒ 先不做：实测兄弟仓 469 条真实派发里只有 1 条给了标签；而且新仓还没有任务列表和通知文案，给了也没人显示。要有需要再加——加回来要动记录格式。

预设——本来打算让父方按名字挑一套写好的设定（钉工具/模型/思考档位/要不要交报告）。

⇒ 先不做：实测 0 次使用，而且本机一个定义文件都没有（~/.pi/agent/agents/ 是空的）。更麻烦的是它会静默失效——外壳不接解析器时，传了名字也不报错、直接按通用子代理起。要这些效果，父方直接传模型/工具名单就行。

「要不要等」这次不做

原来有个参数能让父方挂着等结果（同步拿到，还是只拿编号由它定）。

⇒ 先不做：一律异步——派发立刻返回编号，跑完了通知父方。这样父方永远不会被挂住（挂着等有座位 + 挂着等跑完，两段都没上限）。要拿结果就查编号。

一个参数的名字会骗人，说清楚

  • 只读档位——它挡的是「改」，不挡「读」。pi 的读工具没有目录囚禁：只读的子代理用绝对路径能读宿主机任何可读文件。它不是沙箱。

7主流程：一次派发走过的路

父方递任务进来 给一段任务描述（taskDescription）。还可以给理由、模型、工具名单、时限、allowScripts（要不要能写脚本）等。
过安检 按顺序问每一道。第一道不过就退回，后面的一概不问。
不过 → 退回 说清为什么。不留记录，不占座位。
过了 → 继续 铸编号；建记录。

安检有哪几道

按这个顺序问。第一道不过就退回，后面的一概不问。（第 2 问里的四个判断是同一个纯函数，顺序同上。）

# 查什么 不过就退回的理由
1 只读档位的值合法吗 只认 strict / lenient。写错值不要改成宽松值——那是把「只读」偷偷变成「可写」
2 任务的正文能安全进命令行吗 四种都退回：空的；以横线开头（纵深防御： buildPiArgv 用 -- 分隔，pi 不会当选项；留着防宿主解析变化）；以 @ 开头（pi 把原始位置参数当文件读：正文被丢弃、文件内容变成指令）；含 C0 控制字符（NUL 进 argv 会让 spawn 同步抛，绕过「拒绝不留痕」）；超过 64 KiB（UTF-8 字节）（argv 装不下 ⇒ spawn 抛 E2BIG ⇒ 记 failed 而不是 rejected）
3 timeoutMs 是整数毫秒吗 给了就计时，不给 = 不设限；必须是 1..231-1 的整数（Node 定时器上限，超了不是「很久」而是立刻溢出）
4 会话要收尾了吗 要收尾了就不接
5 递归太深了吗 子代理再派子代理，层数有上限
6 隔离档位的值合法吗 只认 worktree。写错值不要改成别的档——那是把「隔离」偷偷变成「共享」
7 黑板开关是布尔吗 写错值不猜：猜出来的开关会写错父方的意图
8 要隔离时有 git 仓吗 非 git 目录里开隔离，worktree 到运行时才炸
9 allowScripts 是布尔吗 写错值不猜：truthy 就当开了 codemode，那是把「不许写脚本」变成「能写脚本」
10 进 argv / 附加块的文本字段（model / thinkingLevel / why）合法吗 必须是字符串、且不含控制字符：非字符串会在铸编号之后抛错，让「拒绝」变成「记一条 failed」。单个字段上限 64 KiB（UTF-8 字节，同任务正文）
11 项目上下文档位的值合法吗 只认 auto / none。拼错了不该悄悄当成 auto：加载量会变多
12 usageBudget 合法吗 至少要给一个上限（maxUsd / maxTokens 都没给 = 没设预算，不如不设）；上限必须是正的有限数（0 / 负数 / NaN 不 coerce——错值方向是多花钱）；hardFactor ≥ 1（<1 会让硬门早于软门；= 1 是合法值 ⇒ 到点直接进硬门，不给降级交付的机会）；hardGraceMs 是正的有限数
13 合并后的 user message 能进 argv 吗 任务 + why + 隔离契约现在拼进同一个 argv 参数（< 64 KiB，UTF-8 字节）——超了会撞 Linux 的 MAX_ARG_STRLEN，spawn 抛 E2BIG ⇒ 记 failed 而不是 rejected；首字符不能是 @（pi 把位置参数当文件读，正文被丢弃）

安检是纯函数

给它输入，它只回答「过」或「不过加理由」。它不碰记录、不碰座位、不碰子代理。而且被拒了不留任何痕迹——这是「先安检、后铸编号」的原因。

闸的保证范围到 spawn 为止

闸保证：输入形状合规、错值不 coerce、被拒不铸编号/不建记录/不占座位/不 spawn、同 (input, facts) 同判决。

闸不保证：spawn 之后。孩子与父方同 UID、带 bash，能写 records/*.json（伪造 succeeded）、 tasks/<id>/steer.jsonl（伪造收据）、tasks/<id>/output.log（冒充产出 / 放 FIFO 挂死读）、blackboards/*（伪造作者）。父方读到的「收据」是字节，不是证明。

理由这个开关开着吗 理由会进子代理的 user message（不是系统提示词）。这个开关由主方握着。
开着 → 理由留着 理由原样进 user message。记录里不记「被丢掉」。
关着 → 丢掉内容 理由的内容扔掉，但记录里要记一笔「理由被丢了」。
此刻还能再开一个吗 重新读一次「此刻已用多少」，算此刻的池子。不够就排队等——永远等，不拒绝。
有 → 准备起 状态改「在跑」，记开始时刻。
没有 → 排队等 任务排队，父方立刻拿到编号，不用挂着。跑完了通知它。
现在有几个正在启动 到上限了就稍等一下（不影响座位数）。
起子代理 独立进程。给命令、附加块、环境变量（深度 + 编号）。
看着子代理 盯着有没有卡住；同时把子代理说过的话记下来。
卡住 → 收掉 很久没出声 且 没有在调工具，两条同时成立才算。
超时限 → 收掉 父方给了时限才计时。
收子代理的东西 正文 · 报告 · 用量 · 收据。四样分开收，别混。
定终态 → 还座位 → 清理 → 通知 先定终态，再还座位。顺序反了会出缝。
完了 父方立刻拿到编号，跑完了进通知队列（按 100 KB 一批切开，别刷屏）。

主流程上最容易写反的三处

  1. 安检不过 → 退回要在铸编号之前。退了不留记录、不占座位。
  2. 定终态 → 还座位不能反。反了会留下「座位空出来，被抽掉的活却又跑起来」的缝。
  3. 父方一律收通知——它拿到的只是编号，结果在通知里。

8状态怎么流转

在等→ 在跑→ 要停→ 取消了
在等→取消了 在等→失联 在跑→成了 在跑→败了 在跑→失联 要停→败了 要停→失联

四个终态（成了 / 败了 / 取消了 / 失联）哪儿也去不了。往终态上写的迟到消息丢掉，不报错——竞态下这是常事。

怎么到 什么情况 结果
在等 → 在跑 拿到座位了 记开始时刻
在等 → 取消了 还在排队就被叫停 记原因
在跑 → 成了 子代理退出，退出码是 0 记结束时刻
在跑 → 败了 子代理退出，退出码不是 0 记原因：死因摘要 = 退出码 + stderr 末行（provider 401、段错误都写在 stderr 里）
在跑 → 要停 有人叫停 记原因
要停 → 取消了 子代理收完了；或孩子压根还没起就被叫停（建盘 / 等启动名额期间） 叫停过的一律算取消；没起过的清掉开始时刻
→ 失联 主方（原主人）已经不在了，子代理成了孤儿 没法判断它到底干没干完

「失联」是怎么判出来的

主方重启时，翻出上次留下的、还没结束的记录。主方还活着 ⇒ 是别的会话的任务，不装进来（看不见也停不了，装进来会让人「假停」）。主方已经不在了 ⇒ 标「失联」。

怎么判主方还活着？进程号 + 启动时刻，两个都对才算活着。光看进程号会认错人——进程号会被系统重复使用。

在哪等？ 只有一种等：在等待者队列里等座位。
等座位 核心自己排的队。等到有座位为止。

等的时候，任务已经被记下来了

顺序是：先建记录，再要座位。

⇒ 排队等的任务，记录里已经存在（状态「在等」），而且已经写盘了。

⇒ 所以排队中的任务能被查到、看见、停掉。父方回头能看到「派了 12 个，8 个在跑，4 个在等」。

安检不过 座位满了
记录 不建 建（状态「在等」）
写盘 不写 写
占座位 不占 不占（排队中）

叫醒 ≠ 启动 —— 这两件事必须分开

还座位的时候，座位表会：把座位给最早在等的那个，然后返回那个编号。

但它只是「告诉调用方该起谁了」，它自己不会起。真正起子代理是调用方的事。

⇒ 调用方必须接住这个编号，然后去起它。接不住就等于没人起——那个任务拿着座位，永远卡在「在等」。

有两条路能拿到座位，只有一条是通的

路 怎么走 通不通
等座位时 要座位 → 等 → 拿到 → 起 ✓ 通
有人跑完后 还座位 → 座位表报了下一个 → 接住它并起它 △ 容易漏

第二条路最容易漏：还座位的人常常忘了看返回的是谁。漏了的话，后面排队的任务就永远起不来——它拿着座位，状态卡在「在等」，看起来像在跑其实没有。

并发的五条规矩

  • 满了排队等，永远不拒绝。这是核心跟别的派发做法最不一样的地方。
  • 先来的排前面。
  • 还座位要带提拔：给最早在等的那个，并把它是谁报出去。
  • 抽干的时候（会话要收尾）只还座位，不提拔。否则会有人占着座位却永远不启动——那时候会话都要关了，起起来的子代理没人收，是孤儿。
  • 抽一个还在排队的：抽得掉。已经起了的抽不掉。

核心
拼命令 基础命令 + 减量旗标 +（可选）模型 +（可选）工具名单 + user message 放最后
拼恒定契约块 你是被派出去的，看不到父方对话，你的最后一段话就是交付物 + 报告契约（每次派发逐字节相同）；理由与隔离契约进 user message

命令怎么拼（每一条都有理由）

带什么 为什么
基础命令 -p --no-session --mode json 不留在磁盘上；输出是机器能读的事件流
--append-system-prompt 挂恒定契约块 上下文块 + 报告契约，每次派发逐字节相同 ⇒ 系统提示词恒定，跨子代理共享同一段前缀
--no-extensions --no-skills 减重：砍掉自动发现带进子代理的散文与技能（实测子代理输入从 32575 降到 4356 字符，−86%）
-e <本扩展> 把本扩展自己装进孩子，回执工具（child_report）才在——tool 通道首选、prompt 通道兜底。命令行显式给的扩展不受减量旗标影响
-e 内建:codemode（看 allowScripts） allowScripts 是 true 才带。命令行显式给的扩展不受减量旗标影响，所以减量效果不丢。同时工具名单里也要有它——两处都要
--no-context-files（可选） 不加载项目说明文件（省固定税）。注意：只关「注入」不关「知识」——文件还在工作目录里，子代理会自己去翻（实测输入只差约 15%，不是省一半）
--no-mcp（可选，要版本门） 砍掉 MCP。只有 pi 1.1 及以后才有这个旗标，版本不够就不发（发了会报错）
--model 模型:思考档位（可选） 定模型。解析序：这次调用给的 → 会话当前模型。思考档位先按模型目录校验：只发模型支持的档位（降级目标 low，只降不升）；模型不在目录里就原样透传，并在回执里说「未校验」
--tools 名单（可选） 只给这几个工具。名单里必须包含写程序那个能力和回执工具，否则会被砍掉
user message 放最后（任务 + why + 隔离契约） why 与隔离契约从系统提示词搬到 user message：系统前缀恒定才能跨子代理共享缓存。任务不能以横线开头（安检已经拦过）

前缀稳定化：系统提示词恒定，变化的内容进 user message

provider 的 prompt 缓存按请求前缀命中。以前 why（和条件出现的隔离契约）在 --append-system-prompt 里 ⇒ 每个子代理的系统提示词都不同 ⇒ 彼此之间前缀不共享。 搬到 user message 后，所有子代理共享同一段前缀（上下文块 + 报告契约 + pi 自己的前言 / 工具 / 项目上下文）。

轮内前缀本来就稳定（argv 是启动参数，运行期不变）；这项改造的收益是跨子代理共享， 能否真命中取决于 provider 的缓存键与 TTL（需真机验证）。没有 why、没有隔离时，user message 逐字节等于任务原文 ⇒ argv 与改造前完全相同。

代价：隔离契约的权威性从 system 降到 user message（真机验 isolation=worktree 的子代理仍自行 commit、不 push）。

缓存复用可观测：首轮复用率 + 前缀形状

前缀稳了不等于缓存命中。命中与否此前完全不可观测——只看得见总用量，分不出「首轮就共享上了」和「全程都能复用」。所以引擎从事件流留逐轮明细（observedTurns），算两个数：

首轮复用率 = 首轮 cacheRead / (input + cacheRead + cacheWrite)。只看第 0 轮——后续轮天然会升高，混在一起会互相抵消，把首轮冷启动掩盖掉。增量命中率 = 本轮 cacheRead / min(上一轮 prompt, 本轮 prompt)；取较小值是因为本轮 prompt 可能被 compaction 截短，此时上轮全部都可能被复用。

前缀形状（tools 排序后 + isolated + repoRoot）是天然的组 key。不做哈希：组数很少，存形状更可读、能直接看出分叉维度，也少一个可被等价变异的哈希实现。

⚠️ 复用率低不等于前缀有问题。三种情况都会低：形状是孤儿（没有兄弟可共享）⇒ 形状问题；亲和头失效 / 路由翻转 ⇒ 路由问题；这个前缀从没被写过（新任务、新仓库）⇒ 正常。所以单看复用率只能判「机制状态」，判不了原因——原因要看形状分组。

只进记录，不进正文。判定与形状随回执的 cache 字段走，不改孩子的交付物——正文逐字节就是孩子写的那些字，不掺观测注释。

思考档位：派发前按模型校验

pi 的 clampThinkingLevel 会往上找可用档位：vendor-local 的 medium 是显式 null ⇒ 会被抬到 high （16384 token 预算）。所以派发前先按模型目录校验，只发支持的档位——pi 的 clamp 不再插手，回执里的「实际生效档位」就是孩子真跑的档位。

请求档位 实际发给孩子的 回执
没给 不拼后缀（沿用会话默认） 不擅自替父方降档
模型支持 原样 adjusted: false
thinkingLevelMap 显式 null 降到 low 说明「该模型没有这档」
xhigh / max 缺键 最接近的一档（通常是 high） 按 pi 口径
模型不在目录里 原样透传 modelKnown: false（未校验）
非思考模型 不拼后缀（= off） 说明该模型不支持思考

三条硬规矩：只降不升（生效档位的成本序不得高于请求档位）；降级目标是 low （能干活又不肉疼，不是「最近的一档」）；只发 supported 里的档位。

隔离与黑板：argv 零新增

  • 隔离不改 argv：cwd 走 spawn 的 options（不给时连键都不出现）。工作区由 git worktree add 建好，命令本身一条旗标都不加。
  • strict + 黑板：--tools 名单末尾追加 blackboard_read,blackboard_write——这是 strict 唯一的例外（黑板写的是 dispatch 桶里的板，不是被隔离的工作区）。
  • 黑板不加提示块：契约全在工具描述与读信封的 trust 常量里——孩子每次读都会看到 trust=unverified，不需要往提示词里塞散文。

起子代理这一段的三条硬规矩

  1. 要听 close 事件，不要听 exit 事件。exit 会比管道里的数据先来，一来就收工，丢掉最后的报告和用量（它们都在最末尾）。
  2. 起不来要报错，不能崩。找不到命令之类，只报失败，不许抛未捕获异常把主方带走。
  3. 错误输出只留尾巴。喷涌的输出会把主方的内存撑爆。

还有两条容易漏的

  • 退出可能早于你订阅。所以「晚订阅」也要补发一次退出码，否则会永远等不到。
  • 被信号杀死的，退出码按 POSIX 记 128+信号号（SIGKILL=137、SIGTERM=143）——close 事件对这种情况给的是「码为空、带信号名」，要自己换算；起不来才记 -1。
  • 顺序不能反：先改状态，再起子代理。反了会起出一个没人管的子代理。

strict + allowScripts 不是 shell 逃逸

codemode 只能调 ctx.tools 里的工具（宿主 dist/extensions/codemode/execute.js 的 getCodemodeCallableTools(ctx.tools)）；strict 的 --tools 白名单（child.ts 的 strictToolsArgv）里没有 bash。能力边界的唯一出处是 --tools，不是 allowScripts。

11细看：怎么判卡住

两条同时成立？ ① 很久没出声（没有新的输出字节）
② 没有正在调用的工具
成立 → 卡住，收掉 写明「多久没动静」。
不成立 → 继续看 正在调工具 ⇒ 在等慢工具，不算卡住。

为什么不能把「在等模型回话」当豁免

子代理等模型出第一个字的时候，本来就是安静的。上下文压缩的时候也安静。

如果把这两段算豁免，「生成到一半卡死」就永远收不掉。

⇒ 阈值必须大于这两段的时长。默认 5 分钟。

这一段抓不到什么

子代理反复调同一个工具——它一直在出声，不算卡住。那要靠人或者模型判断，计时器做不了。不要为了抓这种情况而放宽判定。

12细看：收子代理的东西

正文 子代理最后一段话。没有就用全部输出。这是交付物。
报告 三段式：summary 是什么 · why 为什么 · assessment 怎么样。优先读工具通道；没有就从正文末尾抠 JSON 块；都没有就是没有。
用量 主方把事件流里每一轮的 usage 逐轮累加（每轮是单次请求量，不是累计值），存进记录——与孩子交没交报告无关。孩子自报为空/零时，报告里的用量也用累加值顶。
收据 调了哪些工具各几次 · 碰了哪些路径 · 错了几次 · 正文多长。转向过的任务另带 steers（见第 16 节）。

通道 什么时候
tool 子代理主动调了报告工具
prompt-json 没调工具，在正文末尾写了 JSON 块

报告三段式：是什么 · 为什么 · 怎么样

段 内容 性质
summary 一句话结论 判断
why 自己结论的理由。收到 <pi-dispatch-why> 块时以它为输入（回应父方真实动机）；否则纯凭任务书自评。 判断
assessment 干得怎么样：质量判断、踩的坑、偏离、没验证的部分。主锚同 why 段。反话钉：必须点名至少一条具体问题/风险/局限/待复核——全是正面视为没写。 判断
findings 承重证据（claim + 出处） 证据
files_touched / verified / usage 给父方机器核对用，不是散文。verified = 交付前跑过的自检（命令原样），对质走收据里的 bash 命令 回执

三段散文各限 2KB——report 本身是限字摘要，这是「有回执给小窗」的前提。

两条轴：status 说进程怎么了，deliverable 说交付有没有实测支撑

status 只有退出码一个来源（succeeded = 退出 0），它不是质量结论： 孩子什么都不干、打空输出、退出 0，账上照样是 succeeded。交付判据是另一列， 定终态时由 registry 用 deliverableOf 算一次，永不改 status。

  • verified：有自述，且每条都在收据里对上了；
  • unclaimed：有报告但没有可核对的自述——只读分析任务的诚实形态，不罚；
  • partial：有自述只对上一部分（deliveryPartial / verifyPartial 带 {claimed, matched}）；
  • unverified：有自述零命中、assessmentVacuous、或工具报告早于最后一次转向；
  • absent：没交报告、正文也是空的——空跑。

只有 verified 与 unclaimed 享受 8KB 小窗，其余落 50KB 大窗。 assessmentVacuous（缺/过短/全正面）仍是粗筛：它拦「连敷衍都懒得敷衍」的报告， 不鉴定伪问题。

收据的口径决定这套判词可不可信：

  • 路径只收写类工具的 args.path。read/grep/find/ls 不算—— 读过不等于改过，否则把声称改过的文件读一遍就能对上；
  • 两处上限（路径留前 20、命令留最近 20）撞到时置 pathsTruncated / commandsTruncated，截断就不判「对不上」——丢的是证据，不是罪证；
  • bash/sed 改的文件进不了收据（没有 args.path）， 自述这些文件会被判没有实测支撑。旗标的意思是「没有实测支撑」，不是「一定在撒谎」。

读法：whySuppressed=true 时，why/assessment 都是无动机自评（孩子没见过父方的 why），降权精读。

模型面归约：正文不整包进上下文

工具结果在会话历史里每轮重发——大正文是持续的税，且 pi 对扩展工具结果没有尺寸守卫。所以 dispatch_task 返回的正文按预算截窗：

回执质量 预算 形状
四要件全满足（回执在 ∧ 非空转 ∧ 核对没挂 ∧ 自检没谎报） 8KB 头 4KB + 省略标记 + 尾 4KB
无回执或回执不达标 50KB 头 1/4 + 省略标记 + 尾 3/4

省略标记写清总字符数与全文去向。硬规矩：没有 outputPath 就不截——交付物必须可达。全文读回走 dispatch_read。

dispatch_read：读盘的原始流是 JSONL，先散文化成正文，再给每行打 N:hash| 内容锚（omp hashline 口径，空白不敏感）。照抄锚用 around="142:9f3a" 拉该行 ±20 行窗口；锚失配拒绝并回鲜锚——钉住引用不漂移。

收据唯一要紧的一件事：别乱报警

子代理说「我改了这些文件」，但收据里一个都对不上时，要提示「没有实测支撑」。

但这个判断很容易误伤。实测过：直接拿子代理的文件名去对收据里的路径，会误伤 67%（子代理说 src/a.ts，它实际碰的是 a.ts）。

命令对质是段级 × token 级：按 && || ; | 切段、段首 VAR=value 剥掉，命令必须「是」某段的前缀、或同首 token 的参数交错序列——echo pnpm test 只是提到，不算跑过；空白归一 + 截尾省略号宽容仍保留。不认 time/sudo 等 wrapper 前缀，换行不拆（heredoc 由段首挡住）——已知边界，误报出现再补。

⇒ 用后缀匹配：子代理的文件名是收据路径的后缀就算命中。这样零误伤。

13细看：留痕

账本落在一个全局目录、按项目根分桶（不是项目目录里，也不是裸 cwd）。存哪个目录取决于外壳给的参数——核心不知道默认该落哪。

桶名照抄 pi 的编码（pi 会话目录同款：-- + 项目根去开头斜杠、 / \ : 全换 - + --）。例： /Users/x/proj → --Users-x-proj--。自己发明编码的最大风险是跟 pi 的约定分叉。

记录变了 → 写盘 先写临时文件，再改名。写到一半崩了也不留半个文件。写盘失败不打断任务。
子代理说过的话 → 也存一份 超上限只留尾巴，并记下「被截断了」。

编号会拼进路径

所以编号要先查一遍：里面有斜杠、竖线、两个点，就拒绝。不要直接拼路径。

留痕目录是同 UID 可写的

读之前先当它是坏文件：lstat 必须是普通文件（FIFO / 设备 / 软链一律跳过，否则一次读就永久挂死启动），单文件有上限（记录 1 MiB、归档 产出 16 MiB + 64 KiB），见 storage.ts 的 readRegularFile。 readOnly: strict 不是沙箱，isolation 只隔离工作目录——两者都不改 文件系统权限。

启动时读回来

读回记录 一个坏文件不许拖垮启动，跳过它继续。
主方还活着？ 对每条还没结束的记录问一次。
活着 → 不装 是别的会话的任务。看不见也停不了，装进来会让人「假停」。
不在了 → 标失联 没法判断它到底干没干完。

挤掉最老的时候怎么处置

什么时候 怎么做 为什么
平时跑着的时候 压缩存起来（终态留最近 500 条，多的挤掉） 留着还能回捞
启动的时候 直接删（一次最多清 500 个，别拖住启动） 开机时压缩太多会卡

压缩存档的三条

  • 先落位，再删原文件。中间死了最多留两份，启动时能容错。
  • 压缩存档走异步链，每次之间让事件循环转一圈。不然连续的压缩会把主线饿死。
  • 用文件的修改时间当存档时刻。存档文件写成就不改写，所以修改时间就是存档时刻。过期在启动时清（默认留 30 天），单次最多清 500 个，别一次清太多。

14隔离：独立工作区

开了隔离，孩子不在父方的目录里干活：每人一个独立 git worktree，改动、暂存、提交都落在自己那儿。 它不是沙箱——只隔离工作目录，不隔离网络、进程与主目录。

环节 做什么 为什么
受理 读一次 HEAD，钉成记录里的 baseCommit。 钉 base：排队期间父仓 HEAD 前进，孩子的起点不跟着漂。
启动 git worktree add -b pi-dispatch/<编号> <桶>/worktrees/<编号> <baseCommit>，在启动名额内做，然后 spawn 时把 cwd 指过去。 建不出来就失败：任务落 failed、绝不 spawn——绝不降级回共享目录。名额内建盘， 没抢到启动名额就一个 worktree 都不建。建盘是 await（最长 30 秒）：回来先复查记录与会话是否还在启动，已被叫停/拆卸 ⇒ 回收刚建的盘、记取消、绝不 spawn。建盘失败时，失败前已落在盘上的半截目录也 非强制回收（回收失败不阻塞，交给清扫）。
收 观测 HEAD / 分支 / status --porcelain --untracked-files=all 的非空行数（数文件，未跟踪目录不折叠成一行）/ 相对 base 的提交数，写进 记录（attach-worktree 只写元数据，不改状态）。 观测永不抛：失败只记 captureError，不回改终态。观测不到 ≠ 干净——看不到就留空，不填 0。四次观测发生在终态写入前（座位还没归还），各用独立的 5 秒上限（建盘仍 30 秒）：观测只是收据，挂死的 git 不许扣住座位。
留 所有终态都保留 worktree 与分支。 父方要 review、要 merge，证据不能在任务结束时被收走。
扫 有账本（热记录或归档）⇒ 保护，不看 mtime；无账本且过了 TTL ⇒ 非强制 worktree remove → 非强制 branch -d。 分支认不出（孩子换过分支 / detached）⇒ 目录照样回收，只跳过删分支。 宁可留垃圾，不可删证据：脏的、未合并的 git 自己会拒 ⇒ 留下。严禁全局 worktree prune；只碰受管根下的目录，用户自己的 worktree 不动。手工删掉的目录只清元数据， 不重建。

三条边界，说清楚

  • 不自动 merge、不代提交：交付前孩子必须自己 commit；merge 归父方（git merge --ff-only），合完自己收尾。
  • 干净检出没有 node_modules：要跑测试，孩子得自己装依赖。
  • 不是沙箱：路径、网络、进程都还看得见主目录；隔离挡的是「改动踩到父方工作区」。

15黑板：会话级共享板

开了黑板，本会话里开黑板的子代理共用一块板：彼此能读对方留的言，父方用 dispatch_blackboard 也能读（只读，只能读本会话当前那块板）。只有一个孩子时别开——没人交换， 板只是噪音；要不要开是父级的策略判断，引擎不替你数孩子。

东西 形状 为什么
boardId 引擎实例（=一次会话）懒生成一个 UUID，整个会话一块板。 v1 不存在跨会话板；父方凭旧编号只能回查当前板。
目录 <桶>/blackboards/<boardId>/owner.json + notes/<createdAt 13 位补零>-<noteId>.json 文件名序 = 时间序；建板即写 owner（pid + 启动时刻），shutdown 原子补 closedAt。
笔记 noteId / author / createdAt / text；单条 ≤8KiB，空白拒。 先写 .tmp 再 rename——崩了最多留一个没用的 .tmp，不留半个 JSON；读只认 .json，坏文件计入 errors 跳过。读侧也守写侧的线：单条正文超 8KiB （兄弟用 bash 绕过写工具）计入 errors；一次读正文累计 ≤32KiB， 超了截断并给 nextAfter 续读。读参数 after 是游标（noteId 字符串）：非字符串直接报错，不从头读——父方会以为读到的是新的一段。
作者戳 写工具的参数里没有作者字段；作者取自孩子环境里的任务编号。 这是工具契约，不是安全边界——它让兄弟之间分得清谁说的，挡不住有心的孩子伪造。
trust 信封 读结果恒带 trust: "unverified"。 板上的话来自兄弟子代理，可能是假的；文件里自报的 trust 与多余字段一律不认。板的内容 永不自动进任何提示词——读的人才知道该多疑。
TTL 活跃板（有非终态记录引用，或 owner 双条件判活且未关板）整板跳过；owner 读不到/坏 ⇒ 也跳过（判不了活 ⇒ 可能活着，计入 skippedUnknown）；只有 owner 可读且被证死 （有 closedAt，或 pid 双条件证死）才按笔记 mtime 过 TTL 清。空板删目录的前提： owner 可读 && 证死 && 无笔记残留；stat 失败的笔记算「未清」。 有人正在用的板一条都不清；死板的垃圾才会被收走。

strict 也读得写

readOnly: "strict" 时白名单也放 blackboard_read / blackboard_write。这是唯一的例外：板在 dispatch 桶里，不在被隔离的工作区；只读子代理也得能跟兄弟交换信息。

16运行中转向

需求只有一句：孩子还在跑的时候，父方插一句话，孩子看到后调整方向继续干——不是等它跑完，也不是杀掉重来。 父方工具是 dispatch_steer { taskId, message }。转向不新增任务状态：它就是记录上的一组收据（steers），和 worktree 一样，用过才出现。

边界 怎么定
方向 只做父 → 子，单向、纯文本。不做广播、优先级、撤回、图片。
受理 只 running；排队中的任务要改方向就 dispatch_stop 后重派，终态一律拒。判据收在纯函数 planSteer（src/core/steer.ts）一处：只 running、trim 后非空、1–4096 字符、JSON 编码后 ≤ 15 KiB、至多 16 条、seq 接着信箱最后一条续号；引擎 steer() 串行调用它，只负责落盘与记账。
送达点 pi 的回合边界：当前 assistant 轮的工具调用全跑完、下一次 LLM 调用前。不打断在飞的长工具（那是 dispatch_stop 的事）。
宿主 一次性宿主（print/json）里父方正阻塞在 dispatch_task，正常没有插话窗口——但不做硬门：状态是 running 就受理，调到了就应当生效。主要场景是长驻宿主（rpc/tui）。
上限 一个任务 16 条；单条正文 trim 后 1–4096 字符。超了明确拒绝，不落文件。

机制：文件信箱 + 孩子扩展的 turn_end 钩子

父方不碰孩子的 stdin：它只往任务目录追加一行，孩子扩展在每个回合边界自己读。

东西 形状 为什么
信箱 <桶>/tasks/<taskId>/steer.jsonl，一行一个 JSON： {"seq":1,"text":"…","at":1763700000000} 追加写；父方写成功才算 sent。信箱在任务目录里，不进 worktree。
seq 父方分配，接着信箱里最后一条 +1；两次并发 steer 在引擎里串行分配，不会撞号。 孩子按「seq > 上次游标」增量读，撞号会丢信。
环境变量 PI_DISPATCH_STEER_FILE 注入完整路径；继承来的同名变量一律擦掉（与黑板的 G5 同规矩）。 孙代理不能继承父信箱，否则读到别人的转向。
投递 孩子扩展在 turn_end 读新增整行，逐条 sendUserMessage(wire, { deliverAs: "steer" })；发送成功才推进游标。 走的是 pi 原生转向队列；失败或半行下一回合重试，不毒化整批。
降级 旧 pi 没有 sendUserMessage ⇒ 孩子不装收件箱，任务照跑。 父方看到 undelivered，不是崩溃。

注入文本的首行是标记 [pi-dispatch-steer #N]，第二行说明「这是父方的补充/修正，不是新任务」， 正文再另起一行（原样，不转义）。只认整行精确标记——正文/前后缀伪造的标记不算； user 回显还必须能对上同 seq 的 queue_update，初始任务正文里写标记不能伪造送达。

收据阶梯：从「写了」到「模型带着它跑了」

state 证据从哪来 证明什么
sent 父方 appendSteer 成功 字节进了信箱。不是孩子看到了。
queued queue_update 的 steering 元素里有该 seq 的标记 孩子扩展读到了，pi 收进转向队列。
delivered message_end 且 role: "user" 的正文首行有标记 消息进了 transcript。
seen 该 user 消息之后的第一条 assistant message_end 下一次 LLM 调用确实带着它发生了。
undelivered 退出时仍是 sent（一个证据都没有） 没送到。明说，不装。

对账在退出时做（先于终态写记录）：证据只升不降，终态不降级；queued 是合法终态——已入队、没进 transcript，不改成 undelivered（通知里的「未送达」是计数口径： sent / queued / undelivered 一起算作没送到）。delivered 但之后没再出 assistant 的保留 delivered，不谎报 seen。同一 seq 只保留第一次的正文与时刻， 对账只补 state 与时间。assistant 的复述不算送达——证据只认 user 回显。

报告可能早于转向：孩子若在最后一次送达之前就交了工具通道的报告，之后继续干活但不再交， 记 reportStale，失去小窗资格（回大窗，暗示父方复核）。没有报告行或没有送达证据就不判。

父方看到的

  • dispatch_steer { taskId, message } → {ok, taskId, seq, state:"sent", path}；拒绝时 ok:false 并说清原因（不在 running / 未知编号 / 空 / 超长 / 满 16 条 / 无存储 / 无孩子扩展）， 不落文件、不进记录。并发两次调用串行受理，得到 seq 1/2，不会撞号。
  • 运行中只报 sent；终态看 dispatch_list 的 steers——只回收据字段（seq/at/state/queuedAt/deliveredAt/seenAt）， 不回正文；reportStale 只在 true 时出现。一次性宿主的终态结果同样带出。
  • 终态通知带一行「转向 N 条：送达 D / 生效 S（未送达 U）」（U = N − D）； 一条都没进 transcript 时写「未观测到送达」，不写「送达 0」。没转向过的任务没有这一行；reportStale 为 true 时另加一句「工具报告早于最后一次转向」。

一个字都不动的地方

任务状态机、argv、stdin（仍是 ignore）、退出语义、stop、超时与停滞判定、worktree 与黑板、 readOnly: "strict" 的白名单——转向全不碰。孩子扩展读信箱用的是 Node 的 fs，不是工具，所以只读档也能收到转向。

17预算：软门 + 硬门

预算按观测到的用量判（孩子事件流里 assistant message_end 的 usage），不认孩子自报。两个上限都给时任一越线即到点。

口径 怎么算 为什么
美元 累计 usage.cost（provider 不上报时按 0 算） 用户真正在意的单位；本机 vendor-local 下 cacheRead 只占成本 13%
token input + output + cacheRead + cacheWrite 必须含 cacheRead：本机 27505 回合实测它占 prompt token 的 97.7%；不含的话缓存型子代理在账上「几乎不花钱」，预算形同虚设

两段式：软门先行，硬门兜底。

18预热：孩子侧关掉

pi 的 cacheWarming 只读 agent 目录级 settings（项目级 .pi/settings.json 里的值不生效）。所以关闭它走扩展钩子 cache_warming_decision：depth > 0 的进程返回 {action: "stop"}，depth === 0（父会话）不表态。

  • 注册在工厂层（跑一次、进程内长期有效），不是 session_start （后者会因 new / resume / fork 重复触发）。
  • 注册处 try/catch：老版本 pi 不认识这个事件时抛错也不影响派发。
  • 不往孩子工作区写 .pi/settings.json：写了不生效，还会污染父方工作区、给隔离档添落点问题。
  • 父会话（depth 0）不注册 ⇒ 预热照旧（父会话长命，预热对它有价值）；子代理短命，热缓存没人用。
  • 机制事实：运行中的续接概率是 1（闲置期才是 0.15）⇒ 孩子在跑时 pi 几乎总判定「预热划算」。收益小（每预热一次约 $0.00006 量级）但严格非负。

19别踩的坑

  1. 听 exit 而不是 close ⇒ 丢掉最后的报告和用量。
  2. 起不来时抛异常 ⇒ 整个主方崩掉。
  3. 错误输出不限量 ⇒ 内存被喷爆。
  4. 退出早于订阅 ⇒ 拿不到退出码。晚订阅要补发。
  5. 拿到座位和改状态之间被抽掉 ⇒ 起出一个没人管的子代理。改状态时要看是不是还在「在等」。
  6. 开关写成值 ⇒ 主方中途改不生效。要写成每次调用时问一次的函数。
  7. 理由被丢掉时连事实一起扔了 ⇒ 父方以为理由送出去了。记事件，不记内容。
  8. 终态上挂报告时报错 ⇒ 竞态下常事，应该静默丢掉。
  9. 先还座位再定终态 ⇒ 被抽掉的活又跑起来。
  10. 叫醒了却没人起 ⇒ 那个任务拿着座位，永远卡在「在等」。叫醒和启动是两步。
  11. 光看进程号判断主方活着 ⇒ 进程号会重复用。要配启动时刻。
  12. 收据用文件名直接对 ⇒ 误伤 67%。用后缀匹配。
  13. 编号直接拼路径 ⇒ 有斜杠就写到别处去了。要先查一遍。
  14. 只带参数、不看工具名单 ⇒ 子代理看得见写程序，但被名单砍掉，白带。两处都要改。
  15. 池子给太大 ⇒ 内存不够，所有子代理一起变慢。宁可给小。
  16. 用重算后的池子去收已经在跑的 ⇒ 中途杀子代理。重算只管「还能不能开新的」。
  17. 重算了却没人叫醒排队的 ⇒ 池子松了队列还卡着。要有人定时叫醒。
  18. 转向用 followUp / nextTurn 投递 ⇒ 孩子本轮看不到，等于跑完才读。要 deliverAs: "steer"。
  19. 最后一个 turn_end 之后写的转向 ⇒ 永远送不到。收据必须是 undelivered；不重放、不复活已结束的 run。
  20. 发送失败也推进游标 ⇒ 那条永久丢。要成功才推进。
  21. assistant 复述标记也算送达 ⇒ 证据造假。只认 user 回显。
  22. 旧 pi 没有 sendUserMessage 还硬装收件箱 ⇒ 孩子崩在 turn_end。先探测能力，没有就不装。
