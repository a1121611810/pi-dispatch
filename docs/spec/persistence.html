1盘上长什么样

账本不落项目里，落在一个全局目录，按项目分桶。存哪个目录取决于外壳给的一个参数——核心不管默认该落哪，只往给定的目录写。

桶的键是项目根（向上找到 .git 或 .pi 的那一级），不是裸 cwd——从子目录启动也落同一个桶，不散账。 

~/.pi/dispatch/                    ← 全局存放目录（外壳注入，核心不知道默认）
├── <项目A根编码>/             ← 一个项目一个桶
│   ├── records/                   ← 记录：一条任务一个文件
│   │   ├── 01a1ec71….json         ← 任务记录（每次变化重写整个文件）
│   │   └── 01a1ec71….json.tmp     ← 写入中的临时文件（写完改名，原子落盘）
│   ├── tasks/
│   │   └── 01a1ec71…/
│   │       └── output.log         ← 子代理的完整输出（超 16MB 砍头留尾）
│   └── archive/                   ← 压缩归档：被挤掉的记录搬来这里
│       ├── 01a1ec71….json.gz      ← 记录 + 归档时刻
│       └── 01a1ec71….output.gz    ← 子代理输出（gzip）
└── <项目B根编码>/             ← 另一个项目，另一个桶，账互不混
    └── …

桶名怎么编码：照抄 pi 的写法

项目根是路径，不能直接当目录名。编码函数照抄 pi（pi 的会话目录就是这么命名的，本机 ~/.pi/agent/sessions/ 里那些 --Users-…-- 就是）：

"--" + 项目根路径(去掉开头的斜杠,所有 / \ : 换成 -) + "--"

例：/Users/x/proj → --Users-x-proj--。可读（人对得上哪个桶是哪个项目），跟 pi 一致（用户在 sessions 目录里见过同款）。撞名罕见（得同父目录下有 a/b 和 a-b），真撞再加 hash 后缀。

编号会拼进路径

tasks/<编号>/output.log——编号直接当目录名用。所以编号里如果有斜杠、竖线、两个点，先拒绝，别拼路径。这是防「写到别处去」的。

2平时：两条写路径

运行时只有两种东西会落盘，各自一套规矩。

记录
记录变了 → 立刻写状态每次变迁都触发（订阅状态本的通知）
先写 .tmp，再改名写到一半崩了，磁盘上最多留一个没用的 .tmp，不会留半个 .json
写盘失败 → 不阻塞任务记录还在内存里，任务继续跑；磁盘这轮缺了，下轮补
输出
子代理出声 → 内存里攒着超过 16MB 就砍头留尾，并记下「被截断了」
跑完 → 写 tasks/<编号>/output.log一次写整份；记「截断」的标记跟着记录走

为什么输出是「砍头留尾」而不是「全留」

报告和用量都在输出的最末尾。头丢了无所谓（是中间过程），尾丢了就丢了交付凭证。所以超限时保尾不保头。

3挤掉最老的时候：两条路

终态记录超过 500 条，把最老的挤掉。挤掉的东西去哪，分什么时候挤：

什么时候 挤掉的去哪 为什么
平时跑着的时候 压缩归档搬去 archive/，还能回捞 留着还有取证价值
启动的时候 直接删 开机时一批批压缩会卡住启动
终态超 500 条了 按「结束时刻 + 编号」排，最老的先出
平时：异步归档 挂进异步链 → 逐个 gzip → 落位 → 删热文件（见下）
启动时：同步直删 挤掉的同时删掉文件，不压缩

注意：排队中的记录永不挤

挤只挤终态（成了 / 败了 / 取消了 / 失联）。还在「在等」「在跑」「要停」的，不挤——那是活账。

4归档的三条规矩

「平时归档」那条路不是随手 gzip 一下就完，有三条规矩，每条都对应一个踩过的坑。

① 先落位，再删原文件 .gz.tmp 写完整 → 改名 .gz → 再删热文件。半途死掉最多留两份（热文件 + 归档），启动读盘时容忍重复
② 走异步链，每次之间让事件循环转一圈 一条链上一个一个来，中间插 setImmediate。不然连续的 gzip 会把主流程饿死
③ 归档文件写成就不改写 所以文件的修改时间就是归档时刻。过期判断直接看 mtime，不用再记一份账

归档失败 ≠ 丢

gzip 挂了、磁盘满了——热文件留着不动。下一轮启动走「直删」路径收尸。归档这条路只允许「多留一份」，不允许「没归档就删了」。

5启动时：怎么读回来

核心重启（或新开会话）时，把磁盘上的记录装回内存。顺序是固定的：

启动给了存放目录才走这条路
读 records/*.json，装回内存一个坏文件跳过，不许拖垮启动
订阅状态本以后记录每次变化都自动写盘
对每条「还没结束」的记录 它的主方还活着吗？
活着 → 不装 是另一个会话的在飞任务。装进来也看不见、停不了，还会「假停」
死了 → 标「失联」 上次会话没来得及收。它到底干没干完，没法知道了
剪历史 + 清过期归档boot 模式挤掉即删 + 清 30 天前的压缩包（单次最多 500）

「还活着」怎么判：进程号 + 启动时刻

只看进程号会认错人——进程号会被系统重复使用。要进程号和启动时刻两个都对，才算这条记录的主方还活着。

这条记录在建的时候就盖好了戳：ownerPid + ownerBootMs。

为什么值得这么麻烦

不留痕的话：会话一关，「派过什么、谁干完了、孩子说了什么」全没了。下一次会话从零开始，重复派活、重复花钱。

留痕换来的：跨重启的账本——父方随时能查「上次那个调研跑完没有」，孩子说过的话也都在盘上。
