## 一、一句话结论

**我们一直在优化「前缀稳定化」这条收益极小的线，真正的大头是「上游路由翻转」——
4 天里翻了 12 次，静默清空了整个 fleet 的前缀缓存，吞掉了 29.1% 的孩子花销（$0.039）。
第一步应该装观测，不是改前缀。**

## 三、决定性实测（我自己跑的对照组）

**实验设计**：网关 `127.0.0.1:3425`，`model=deepseek-flash`，system 前缀 6000+ token，
全部带 `x-session-affinity` + `session_id`。每次只改一个变量。

| 组    | 变更点                    | cacheRead        | 结论                    |
| ----- | ------------------------- | ---------------- | ----------------------- |
| A     | 无（基线）                | **896 恒定**     | 基线                    |
| **B** | **user message 只改 why** | **896 恒定**     | ✅ **why 不破缓存**     |
| **C** | 先热身同前缀，再换 why    | **896 恒定**     | ✅ 确认                 |
| **D** | **system 尾部改 1 字符**  | **0 / 896 交替** | ❌ **改 system 破缓存** |
| E     | tools 描述改 1 词         | 896 → **768**    | ⚠️ 只丢 tools 那一段    |

**⇒ 改造③ 的核心主张成立**：why 放 user message 不破缓存，改 system 才破。

**pi 的位置探针**（改哪一段，损失多少）——本轮最有操作价值的产出：

| 差异位置                   | cached%   |
| -------------------------- | --------- |
| **（完全不变）**           | **100%**  |
| `project_context`          | 43.1%     |
| `addendum`（我们的契约块） | **12.9%** |
| `cwd`                      | 6.5%      |
| （user message）           | 6.4%      |

**⇒ 段序决定一切**。我们的 `CONTRACT_BLOCK` 在第 5 位，前面 2282 字符
（preamble/tools/rules/docs）在任何 addendum 变化时都能共享。

## 四、真正的分叉点：工具桶（mcode 发现，我独立验证）

**pi 把工具清单以「文字」形式焊进 system prompt 第 2 段**，不是只放在 API 的 `tools` 参数里：

```
<tools>
- read: Read file contents
- bash: Execute bash commands (ls, grep, find, etc.)
...
</tools>
```

400 条真实日志的实测：

| 工具集家族                      | 运行数 | 占比  |
| ------------------------------- | ------ | ----- |
| `bash,edit,read,write`          | 338    | 84.5% |
| `find,grep,ls,read`（strict）   | 29     | 7.2%  |
| `bash,codemode,edit,read,write` | 27     | 6.8%  |
| `codemode,find,grep,ls,read`    | 6      | 1.5%  |

**跨家族 LCP = 191 字符 = 3.9%**（分叉点在 `- bash: Execute bash commands`）。

按「有无同 cwd 兄弟」×「工具桶」交叉分组，实测首轮复用率：

| 组                        | n   | 中位      | >0.5   |
| ------------------------- | --- | --------- | ------ |
| normal 桶 + 有同 cwd 兄弟 | 55  | **0.893** | 53%    |
| normal 桶 + 独苗          | 283 | **0.495** | 31%    |
| **strict 桶**             | 35  | **0.064** | 17%    |
| **codemode 桶**           | 27  | **0.305** | **0%** |

## 五、优先级反转（codex 的核心贡献）

| 维度                              | 绝对金额    | 占孩子花销 |
| --------------------------------- | ----------- | ---------- |
| **🔴 上游路由翻转（4 天 12 次）** | **$0.0390** | **29.1%**  |
| 🟡 strict 桶分叉                  | $0.00038/孩 | <1%        |
| 🟡 隔离 cwd 分叉                  | $0.00017/孩 | <0.5%      |

**⇒ 后两者加起来不到路由翻转的 1/50。**
⇒ 我们之前（包括我自己）盯着 strict 桶讨论了半天，**量级上完全不值得动**。

**路由翻转的机制**：孩子形状的请求在 11-21→11-25 期间上游翻了 12 次
（deepseek↔kimi↔minimax-code）。每次翻转发到新上游 ⇒ 整个 fleet 的前缀缓存清零。
翻点后实测：`in=3010/cr=189`、`in=3793/cr=226`、`in=2375/cr=189` —— 典型冷启。

**codex 另测**：直连 `deepseek/deepseek-flash` 稳定度 **98.9%**，
`regex:group/main` 明显更低（路由会漂移，而 KV cache 是实例本地的）。

## 七、方案（分三步，按「先便宜后贵、先证伪后施工」）

### 第一步：装观测（唯一被六家一致推荐的一步）

**目标**：把「缓存有没有共享」变成会响的数字。

**改什么**：

1. `src/core/child.ts` 的 `UsageTracker` 加 `turns: TurnUsage[]`（现在只累加总额，逐轮明细被丢弃）
2. 新增 `src/core/cache-metrics.ts`——纯函数、不 import pi、与 `budget.ts`/`thinking.ts` 同层
3. 回执加两个字段：`cache: { verdict: "healthy"|"partial"|"not-reusing", reuse: number }`
   （**只放判定 + 一个数**，不塞逐轮明细——父方 context 有限）

**判据（写进检查，不写进文档）**：

- 首轮 `cacheRead == 0` 且首轮 `input > 2000` ⇒ 回执带一行「前缀未共享」
- `prefixHash` 变化 ⇒ 标注分叉维度（tools / cwd / project_context / upstream）

**顺带白拿的数据**：`sections` 原文已经在事件流里（`child.ts:393-394` 已在解析），
⇒ `prefixHash = sha256(preamble..addendum 的逐字节拼接)`，
**精确取自孩子自己看到的提示词，不是从 argv 反推的近似**。

**代价**：一个数组 + 一个纯函数模块 + 3 条破坏点 + 回执 2 个字段。**不花钱，不加真机开销。**

**为什么值**：38.2% 的花销是首轮前缀税，34.4% 是理论天花板，
而**今天仓库里没有任何一个判据是关于「前缀有没有共享」的**
（`cost-control.md` 全部围绕 input/output 调档位调模型）。

### 第二步：钉住上游路由（先量后改）

第一步装好观测后，看「冷启动」事件到底由什么触发。

**候选动作**（按代价排）：

1. **子代理直连模型**（`deepseek/deepseek-flash`）而不是走 `regex:group/main`
   —— codex 实测直连稳定度 98.9%
2. **路由组内固定一个上游**，或按「形状」而不是按「组」路由
3. 在回执里加「上游 provider」字段，冷启动时一眼看出是路由翻转还是形状变了

**⚠️ 但这一步必须等第一步的数据**——现在改就是猜。

## 八、明确不要做的事（六家一致或强共识）

1. **❌ 不要为了缓存统一工具档位** —— 拿真能力换 $0.00038，方向反了
   （`cost-control.md` §五.5 已实测「省三位数，砍真能力」）
2. **❌ 不要把隔离契约搬进 system prompt** —— 缓存侧净收益 ≈ 0
   （隔离组 cwd 段本来就分叉，只差 2.1%）；且会把「system prompt 逐字节恒定」
   这个**可断言的不变量**变成集合
3. **❌ 不要去找「保留 KV Cache 更新 system prompt」的 API 参数** —— 有（`in-history`），
   但 vendor-local 没暴露
4. **❌ 不要引入 DeepSeek 的 PromptSection/PromptContext 分层框架** ——
   那是为长命多轮 Session 设计的，我们的子代理是一次性进程，`systemUpdates()` 是纯无用代码。
   **要学它的「破缓存清单」，不是它的「分层 API」**
5. **❌ 不要把 `affinity.json` 的 turn 字段当子代理轮数** —— 那是 body 指纹的伪影
6. **❌ 不要往子代理提示词里塞常驻内容来「把前缀做大」** ——
   codex 实测 125K token 的大 prompt `cacheRead` 只有 186（**超缓存上限，完全不命中**）；
   且 DeepSeek 官方「硬盘缓存默认开启」下，多付的是 cacheRead 的 1/10 单价，换不来命中率

## 九、一条口径修正（必须写进文档，否则会误导后来人）

**「system prompt 逐字节恒定」这句话要改口径。**

我们恒定的**只是 `addendum` 一段**。其余四段都在前缀里，且不由我们控制：

| 段                | 状态                                      |
| ----------------- | ----------------------------------------- |
| `preamble`        | ✅ 恒定（100%）                           |
| `tools`           | ❌ **随工具桶变**（4 个取值）             |
| `rules`           | ❌ 随工具桶变（4 个取值）                 |
| `docs`            | ⚠️ 2 个取值                               |
| `addendum`        | ✅ **我们恒定它**（改造③ 的成果）         |
| `project_context` | ⚠️ 跨仓不同，同仓恒定                     |
| `cwd`             | ❌ **362 个不同值**（隔离档每个孩子一个） |

⇒ 我们的 `CONTRACT_BLOCK` 放在第 5 位是**对的**——
它把工具桶和项目上下文的分叉点都留在了自己前面，没多丢东西。

（`a21a8c9`，11-25 07:32）；最后一条含 why 的记录是 11-24 14:42。

| ------------------------------------- | --- | --------- |

| 不带 why（system prompt 逐字节相同）  | 9   | **1.000** |

方向明确（why 留在 system 里轻微拖累，挪走就完全命中），但样本小。

## 附二：kimi 的机制质疑成立（推翻我文档里的旧说法）

### 质疑

kimi 独立提出：**「命中是整块不是连续前缀」这个观察本身可能是误读。**

> "实测值 {128,186} / {0,128,186} / {128,186,4992} 与 128-token 分块对齐的前缀缓存一致，
> 4992/4998 说明是『块对齐的部分前缀命中』，不是『整块或全无』。
> ……0% 与 77% 的双峰更可能来自【亲和路由落点不同】（不同上游实例 ⇒ 连 186 都没有）而非字节不同。
> 这把 Q2 的重点从『字节一致性』移向『路由粘性 + 组数』。"

### 判定：kimi 对了，而且我的 E 组就是决定性证据

**我的 E 组**：只改 `tools` 参数的 JSON 描述一个词 ⇒ `cacheRead` 从 **896 掉到 768**（掉 128 = 一个块）。

| 假设                      | 预测                                        | 实测            |
| ------------------------- | ------------------------------------------- | --------------- |
| 「整块或全无」            | 改一个词 ⇒ 整个前缀失效 ⇒ **cacheRead = 0** | ❌ 实测 768     |
| **「部分前缀 + 块对齐」** | 只丢 tools 那一段之后的 ⇒ **768**           | ✅ **实测 768** |

**⇒ 缓存是部分前缀命中。** 我文档附一里写的「命中是整块不是连续前缀」**是错的**。

### 正确的机制表述

```
命中量 = min(本次前缀长度, 历史上已缓存的最长匹配前缀) 向下取整到块边界
已缓存前缀 = 历史上某个「恰好在此处分叉」的请求
```

**⇒ 「没有连续中间值」不是「整块或全无」，而是「能命中的长度只取历史上出现过的分叉点」。**
⇒ **0% / 19% / 77% 的双峰/多峰，主要是路由落点不同（不同上游实例），不是字节不同。**

### 这条修正的影响

1. **Q2 的重心要移**：从「字节一致性」移到「**路由粘性 + 前缀组数**」
2. **段序比「整段恒定」更重要**：变量内容放越靠后，能保住的前缀越长
   （这与 pi 的位置探针表完全一致：改 addendum ⇒ 12.9%，改 cwd ⇒ 6.5%）
3. **解释了 codex 测到的「路由翻转 = 29.1%」为何是大头**：
   换了上游实例 ⇒ 连 186 token 的常量块都保不住 ⇒ 归零

### kimi 的另一条独立判断（与其他五家相反）

> "我认为改造③的收益上限比多数人预期的低：实测网关全局命中已 96.4%，真实子代理首轮
> cacheR(8320) > in(4640)，说明常量块已经在命中；90% 单轮子代理的增量成本在
> **唯一那段文本**（4640 tok 量级的任务+why+契约值），前缀纪律再优化也碰不到它。
> 所以我把『**缩短唯一段/减少重复 boilerplate**』排在『再优化前缀』之前。"

**⇒ 这是六家里唯一把优先级指向「砍唯一段」的。** 值得重视：
它指出「前缀纪律」的边际收益有上限，**真正剩下的是每孩子都要全付的那段唯一文本**。

### kimi 的第四条「不要做」（机制性论证，很干净）

> "不要引入跨会话的显式 cache warm-up 请求：**亲和头按会话划分，预热请求与子代理不共享亲和键
> ⇒ 路由到不同上游实例 ⇒ 预热无效**（且首个子代理本身就是预热）。"

**⇒ 这从机制上论证了「跨会话预热无效」**，比「关掉预热省钱」这个理由更根本。
（注意：与「同一会话内预热」不同——同一会话内预热是有效的。）

### kimi 的 Q3 答案：按「不变量/变量」拆，而不是按「整块/整块」拆

- **system prompt（恒定）**：隔离契约里的**规则**——「你运行在隔离 worktree 里，不得越界」
- **user message（变化）**：隔离契约里的**值**——worktree 路径、隔离 id、清理方式

**⇒ 这是 DeepSeek 的 PromptSection/PromptContext 拆分在我们场景下的精细化版本。**
**⇒ 但注意：这与 pi 的实测有张力**——pi 实测「隔离块整块放 system」会掉到 30.6%，
而 kimi 建议的是「只把规则放 system、值放 message」，
**⇒ 关键在于规则文本必须对所有子代理逐字节相同**（否则照样分裂成两组）。

## 附三：根因归因 —— 不是「vendor-local 路由不稳」，是「上游配额不够 + 我们自己把高峰流量锁在最易挂的那家」

**⇒ 这是本轮最便宜的一个可动点：改配置，不写代码。**

### 五、但要算清这笔账：路由组的成本换来的是「不失败」

```
不走路由组：配额一耗尽 → 硬失败（429 直接报错）
走路由组：  配额一耗尽 → 换上游 → 多付缓存冷启动成本
```

**⇒ 路由组的成本是「缓存冷启动」，它的价值是「不失败」。**
⇒ 要降低这个成本，**不是取消路由**（会换来失败），
而是 **① 让冷启动少发生**（固定上游 / 放宽时段规则）或 **② 让冷启动便宜**（上游缓存保留期更长）。

| kimi-for-coding    | 91   | **true**                   |

**⇒ `stoodIn: true` = 「这个成员是顶替上的」** —— 顶替行为直接写在数据里。

## 附四：最终归因 —— 路由组是**有意的最优解**，副作用集中在两条时段规则

> 用户澄清：`main-tier` 的设计意图是「贪 minimax 和 kimi 的 coding plan（5 小时 / 7 天 / 月度三重限额），
> 429 就自动切下一个，deepseek 作为两个用完后的兜底」。
> **这是配额约束下的贪残策略，逻辑完全站得住。**
> 本节回答：既然如此，还要动什么？

### 一、vendor-local 的 affinity 只有 `session` 一个取值

实测 `~/.config/vendor-local/providers.json`：18 个组全部 `"affinity": "session"`，
`routing` 只有 `expiring`（2 个）和 `order`（16 个）两种。

**⇒ 没有「按前缀形状亲和」这种选项。**
⇒ 「让同一形状的孩子固定落同一上游」这件事，**vendor-local 现在做不到**，
只能靠「直接指定模型」绕过路由组（代价是失去容灾）。

### 二、冷启动的真实规模（我独立统计 46,979 条 pi 请求）

| 指标                             | 数值                     |
| -------------------------------- | ------------------------ |
| 冷启动请求（`cache_read < 500`） | **828 / 46,979 = 1.76%** |
| 它们付的全价 input               | 9,925,419 token          |
| **占全价 input 的比例**          | **10.3%**                |
| 整体可缓存比例                   | 94.2%                    |

**⇒ 请求数只占 1.8%，但花钱占 10.3%。** 冷启动请求的 prompt 特别大
（首个请求 in=19770 / 40436 / 5936 等），所以「少而贵」。

### 三、成本区间（我的上限 vs codex 的下限）

| 口径         | 估算           | 说明                         |
| ------------ | -------------- | ---------------------------- |
| 我的上限     | **$0.107/天**  | 假设冷启动请求本该命中 94.2% |
| codex 的下限 | **$0.0097/天** | 只算实际可回收的子集         |
| **真实值**   | **在两者之间** | 约 $0.01 ~ $0.11/天          |

**⇒ 即便取下限，也是 $0.0097/天 ≈ $0.04/4 天。**
**⇒ 而项目此前记录的总花费是 $0.1497（233 条派发）⇒ 冷启动占 2.6% ~ 7%。**

### 四、冷启动的时间分布 —— **精确命中那两条时段规则**

按小时的冷启动率（46,979 条 pi 请求）：

| 时段      | 冷启动率   | 是否在时段规则内                  |
| --------- | ---------- | --------------------------------- |
| 07 时     | 0.23%      | 否                                |
| 08 时     | 0.28%      | 否                                |
| **09 时** | **9.59%**  | ✅ 规则起点（09:00 起 → minimax） |
| **10 时** | **11.87%** | ✅                                |
| **11 时** | **6.21%**  | ✅                                |
| 12 时     | 3.63%      | 规则结束（12:00）                 |
| 13 时     | 2.13%      | 否                                |
| **14 时** | **12.63%** | ✅ 规则起点（14:00 起 → minimax） |
| **15 时** | **15.14%** | ✅                                |
| **16 时** | **8.76%**  | ✅                                |
| 17 时     | 0.17%      | 否（规则 18:00 结束）             |
| 18 时     | 0.50%      | 否                                |
| 20 时     | 5.70%      | 否                                |
| 22 时     | 1.84%      | 否                                |

**⇒ 规则生效的 6 个小时，冷启动率是其他时段的 20~70 倍。**

**⇒ 机制很清楚**：
时段规则把流量**强制切到 minimax-code**，而 minimax-code 的配额最紧（36,315 次 quota 429）
⇒ 它一挂就切到下一个 ⇒ **KV cache 池子换一个** ⇒ 那批请求全部冷启动。

工作日 vs 周末同小时对照，进一步坐实：

| 时段  | 工作日             | 周末               |
| ----- | ------------------ | ------------------ |
| 09 时 | **50.00%** (n=42)  | 6.20% (n=500)      |
| 14 时 | **12.84%** (n=584) | 0.00% (n=10)       |
| 21 时 | **16.98%** (n=53)  | 1.37% (n=438)      |
| 22 时 | **23.59%** (n=390) | **0.02%** (n=4672) |

**⇒ 周末没有时段规则 ⇒ 冷启动率塌到 0.02%。**

### 五、结论

**路由组的设计（贪 coding plan + deepseek 兜底）是对的，不该改。**
**真正可动的是那两条时段规则**——它们：

1. 在配额最紧的两个时段，把流量压到最容易挂的那家
2. 让冷启动率上升 20~70 倍

**⇒ 建议：放宽或去掉那两条规则。**

- 去掉的收益：冷启动率从 9.6~15.1% 回到 0.2~0.5% ⇒ 约省下冷启动成本的 90%+
- 去掉的代价：minimax 在那两个时段可能不是最便宜的（但它本来就在 429 边缘）

**⇒ 这是一个改配置就能生效的动作，不需要写代码。**

### 六、但还有一个更根本的问题（留给观测）

`affinity: session` 意味着「同一会话内粘住」。而**子代理每次运行的 session id 都是新的随机值**
（`pi -p --no-session` → `SessionManager.inMemory()` → `randomUUID().slice(0,8)`）。

**⇒ 子代理的亲和键天然跨会话不共享 ⇒ 只能靠「前缀形状恰好相同 + 落在同一上游实例」复用。**
**⇒ 这就是为什么路由一旦翻转，损失是全体的。**

**⇒ 要真正解决，需要 vendor-local 支持「按前缀形状亲和」——它现在不支持。**
**⇒ 或者：子代理直连单一模型（放弃容灾）。**
**⇒ 这是「装观测」能帮你判断「值不值得放弃容灾」的另一个理由。**

**⇒ 附五的 A1（让高峰期优先用 DS）完全违背意图 —— 撤回。**

### 二、但真相比「规则扭曲」更复杂 —— 冷启动的真正主因不是路由

我对 571 条冷启动请求做归因（看冷启动前 5 分钟内同上游是否有别的请求）：

| 归因                                              | 占比      |
| ------------------------------------------------- | --------- |
| **缓存池是热的，但这条前缀没命中 ⇒ 前缀形状变了** | **81.6%** |
| 真冷启动（缓存池换了/过期）                       | 6.1%      |
| 无法判定                                          | 12.3%     |

**⇒ 路由切换只解释了 6.1%。**
**⇒ 81.6% 是「同上游、缓存池热、但这条前缀没命中」⇒ 是前缀形状的问题。**

按上游细分（缓存池是热的比例）：
`regex:group/main` 93.5%、`minimax-cn/MiniMax-M3.1-Flash` 93.3%、
`deepseek/deepseek-flash` 95.5% —— **三个上游都一样高 ⇒ 不是某家的缓存实现问题**。

### 三、真正区分冷启动的是 prompt 大小

| 组       | n      | `in` 中位 | 命中中位 |
| -------- | ------ | --------- | -------- |
| 冷启动   | 571    | **4794**  | —        |
| 非冷启动 | 46,151 | **774**   | —        |

**⇒ 冷启动的 prompt 大 6.2 倍。**

按 `in` 分档看命中率：

| `in` 区间 | n      | 命中中位  |
| --------- | ------ | --------- |
| < 2k      | 38,023 | **0.966** |
| 2k-8k     | 6,943  | 0.829     |
| 8k-20k    | 936    | 0.523     |
| **≥ 20k** | 820    | **0.167** |

**⇒ 大 prompt 是冷启动的决定性因素，不是路由。**

### 四、按时段的冷启动率差异，真实来源是「谁在那个时段接大盘子」

| 上游                              | 窗口内冷启动率    | 窗口外冷启动率 |
| --------------------------------- | ----------------- | -------------- |
| **minimax-cn/MiniMax-M3.1-Flash** | **32.0%** (n=206) | 8.3% (n=24)    |
| regex:group/main                 | 4.8% (n=3549)     | 0.7% (n=39357) |
| deepseek/deepseek-flash           | 2.5% (n=81)       | 1.6% (n=3167)  |

**⇒ 窗口内 minimax 接了大盘子，而它那批请求的 `in` 中位是 1118（vs 全局 774）⇒ 大 prompt 集中 ⇒ 冷启动率高。**
**⇒ 不是「minimax 缓存差」，是「那个时段跑的 prompt 更大」。**

### 五、DS 作为落点后，缓存变热很快（这削弱了「钉住路由」的价值）

pi 落到 deepseek 的 3,369 个请求，按「同上游连续段」切分：

| 段内第 N 个请求 | n   | 命中中位  |
| --------------- | --- | --------- |
| 第 1 个         | 98  | **0.764** |
| 第 2 个         | 52  | **0.907** |
| 第 3 个         | 45  | 0.899     |
| 第 5 个         | 37  | 0.932     |

**⇒ 冷启动是一次性代价，第 2 个请求就回到 0.9 命中。**
⇒ **「钉住上游」的收益被高估了**（codex 的 98.9% 稳定度数据也是这个方向）。

### 六、DS 高峰时段到底花了多少钱（7,717 条 DS 直连请求）

| 时段                              | 请求  | in    | cacheRead | out   | 成本      |
| --------------------------------- | ----- | ----- | --------- | ----- | --------- |
| **DS 高峰**（工作日 09-12/14-18） | 2,368 | 10.5M | 387.6M    | 2.08M | **$7.96** |
| DS 低谷                           | 5,349 | 25.0M | 484.5M    | 5.97M | $8.79     |

**⇒ DS 总花费 $16.75，其中高峰占 47.5%。**
**⇒ 用户的规则（高峰用套餐）已经把这部分流量从 DS 挪走了 —— 规则在省钱，不是在亏钱。**

### 七、修正后的结论

|                    | 附五的结论                 | 修正后                                                           |
| ------------------ | -------------------------- | ---------------------------------------------------------------- |
| 时段规则           | 「扭曲了锚点，该改掉」     | **❌ 撤回。规则精准避开 DS 高峰价，是省钱的设计**                |
| 冷启动主因         | 「路由翻转」（$0.039/4天） | **❌ 只解释 6.1%。主因是大 prompt（81.6%）**                     |
| 钉住上游           | 「值不值得放弃容灾」       | **收益被高估**（DS 第 2 个请求就回到 0.9 命中）                  |
| **真正的改进方向** | —                          | **减少大 prompt 的请求**（`in ≥ 20k` 的 820 条，命中只有 0.167） |

### 八、所以 A 方案（改 vendor-local 配置）**应该放弃**

**⇒ 改配置既违背用户意图（DS 兜底），又不是主要矛盾（6.1%）。**
**⇒ 真正的可动点在项目侧：让首轮 prompt 别那么大。**

`in ≥ 20k` 的请求占 820/46979 = 1.7%，但命中中位只有 0.167。
**⇒ 这些是「首次冷启动 + 超大 prompt」的组合，是真正花钱的地方。**

**⇒ 下一步该做的观测（不是改配置）：**

1. **首轮 `cacheRead` 占比 + prompt 大小** —— 定位哪些派发产出了超大 prompt
2. 重点看：**是不是某些子代理带了巨大的 context（AGENTS.md + skills + 大 repo_context）**

**⇒ 这也正是六家评审推荐的「装观测」——只不过现在我们知道它要回答的具体问题了。**

## 附七：定位「超大 prompt」—— 结果出乎意料，方向要再修一次

> 用户：「先看看有没有别的方式定位超大 prompt（比如直接查那 820 条是哪些子代理）」

### 一、那 820 条**不是** pi-dispatch 的子代理

从 400 份真实子代理日志直接量：

| 首轮 `in` 阈值    | 子代理条数 |
| ----------------- | ---------- |
| ≥ 2000            | 164 (41%)  |
| **≥ 5000**        | **0**      |
| ≥ 10000 / ≥ 20000 | **0**      |

**⇒ 子代理的首轮 `input` 最大只有 3819，没有一个超过 5000。**

子代理的 system prompt 各段（400 份实测）：

| 段                         | 中位字符 | max  |
| -------------------------- | -------- | ---- |
| `addendum`（我们的契约块） | 1942     | 2303 |
| `docs`                     | 1704     | 1704 |
| `project_context`          | 984      | 3148 |
| `rules`                    | 589      | 726  |
| `tools`                    | 274      | 324  |
| `cwd`                      | 92       | 168  |
| `preamble`                 | 126      | 126  |

**⇒ 子代理的 system prompt 总量约 5,700 字符 ≈ 1,800 token，稳定。**
**⇒ 前面附六里「`in ≥ 20k` 的 820 条命中只有 0.167」——那批不是子代理。**

### 二、那 820 条是谁：**父方 pi 主进程**（不是子代理）

三个独立证据：

1. **`native_session` 匹配的是父会话**：`01a1fe3e-1530-...` 在小 prompt 请求里出现 745 次、在大 prompt 里出现 19 次
   —— 同一个长期会话，不是每次新建的子代理。
2. **子代理日志 0 命中**：抽查 120 份 `output.log`，**没有一份**的 session id 出现在这 820 条里。
3. **请求体构成完全不同**（`up_parts` 字段直接给出字节数）：

|                         | system     | tools       | in 中位 | 命中中位  |
| ----------------------- | ---------- | ----------- | ------- | --------- |
| **大 prompt**           | **50,554** | **112,671** | 1,143   | **0.988** |
| 小 prompt（子代理形态） | 15,489     | **3,132**   | 726     | 0.945     |

**⇒ 大 prompt = 父方会话，tools 定义 112KB（完整 MCP 工具集）。**

### 三、⚠️ 关键反转：大 prompt 的缓存命中**极好**（0.988），不是 0.167

按 tools 字符数分档：

| tools 字符数 | n         | in 中位 | **命中中位** |
| ------------ | --------- | ------- | ------------ |
| 0-5k         | 39,592    | 726     | 0.945        |
| 5k-50k       | 1,408     | 938     | 0.945        |
| 50k-100k     | 589       | 867     | **0.992**    |
| **≥ 100k**   | **3,384** | 1,143   | **0.988**    |

**⇒ tools 越大，命中越好（因为 tools 本身是恒定前缀，能被完整缓存）。**

### 四、那附六里「`in ≥ 20k` 命中只有 0.167」是怎么回事？

**是分母的问题**：`in` 是**未命中的部分**，`cache_read` 是命中的部分。
`in ≥ 20k` 意味着「这次有 20k+ token 没命中」。

而这批请求的**会话内位置**：

| session 内第几个请求 | 数量    |
| -------------------- | ------- |
| **第 1 个**          | **390** |
| 第 2-10 个           | 27      |

**⇒ 大头是「session 的第 1 个请求」。**
⇒ 但第 1 个请求按定义就没有「上一轮」可复用 ⇒ 它只能靠**跨会话共享**拿到缓存。

**⇒ 真正的判据不是 `in` 大小，而是「这是不是冷启动的那一轮」。**
**⇒ 附六里那张 `in` 分档表把「冷启动」和「prompt 大」混为一谈了。**

### 五、修正后的完整因果链

```
冷启动（= 没有可复用的缓存）    ← 真正的成本
   ├─ 81.6%：缓存池热，但这条前缀没命中 ⇒ 前缀形状变了
   │          └─ 而形状变化，主要来自「工具集不同」+「cwd 不同」
   └─  6.1%：缓存池真的换了（路由切换）⇒ 量级小，DS 第 2 个请求就回到 0.9 命中

大 prompt ≠ 贵
   └─ 大 prompt 往往命中更好（tools 是恒定前缀）
```

**⇒ 结论再修一次**：不是「砍 prompt 大小」，而是「**让更多形状共享同一个前缀组**」。

### 六、那观测要回答的问题也随之改变

| 之前以为要回答              | 实际要回答                                           |
| --------------------------- | ---------------------------------------------------- |
| 哪些派发产出了超大 prompt？ | **哪些派发的前缀形状是「孤儿」（没有兄弟可共享）？** |

**具体判据**：

1. 首轮 `cacheRead` 占比（`reuse`）—— 低的说明没共享上
2. **`prefixHash` 有多少个不同值** —— 这是「前缀组数 G」，直接决定共享机会
3. 冷启动请求里，**同组有兄弟** vs **是孤儿** 的比例

**⇒ 这仍然指向「装观测」，但观测的内容更精确了：**
**「首轮复用率 + 前缀组数」，而不是「prompt 大小」。**
